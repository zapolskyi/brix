Чому зроблено саме так. Кожен запис: рішення, контекст, альтернативи,
наслідки. Нові дописуються згори вниз, старі не переписуються — якщо

## 1. Один репозиторій над `wp-content`, а не окремо тема й плагін

**Дата:** 16.09.2026 · **Фаза:** 0

ТЗ вимагає і власну тему `brix`, і окремий плагін `brix-core`. У попередніх
проєктах (TORQ, Площина) git лежав у корені теми, бо тема була всім проєктом.
Тут так не вийде: половина логіки за задумом живе в плагіні.

**Рішення.** Git-корінь — `app/public/wp-content/`. `.gitignore` спершу
ігнорує все (`/*`), потім точково повертає `themes/brix/` і `plugins/brix-core/`.
Ядро WordPress, WooCommerce, аплоади й кеш у репозиторій не потрапляють.

**Альтернативи.**
- *Два репозиторії.* Два посилання в портфоліо і ручна синхронізація версій
  теми й плагіна, які змінюються одним і тим самим комітом.
- *Код плагіна всередині теми.* Суперечить меті кейсу — показати саме
  розділення презентації та бізнес-логіки.

**Наслідки.** Один `git log` на весь проєкт. README лежить у корені репо,
а не в темі. Архів для хостингу збирається окремо для теми й для плагіна.

## 2. Збірка на `sass` CLI, а не Vite

**Дата:** 16.09.2026 · **Фаза:** 0

ТЗ називало Vite. На TORQ перевірено простішу схему і вона вижила
до продакшену.

**Рішення.** `npm run css` компілює `assets/scss/main.scss` →
`assets/css/main.css`. **Скомпільований CSS комітиться в репозиторій.**
JS — ванільні файли без бандлера, підключаються там, де потрібні.

**Чому.** Тема має працювати на хостингу без Node. Заливаєш архів — сайт
живий. З Vite будь-який деплой вимагає кроку збірки, а забутий
`npm run build` дає сайт без стилів.

**Альтернатива.** Vite з `dist/` у `.gitignore` і збіркою в GitHub Actions.
Це правильно для застосунку, але надлишково для теми з одним CSS-файлом
і кількома скриптами.

**Наслідки.** У дифах з'являється скомпільований CSS — його не рев'ювимо,
дивимось лише на `.scss`. Hot reload немає, є `npm run css:watch`.
Мінімізація й критичний CSS — окремими скриптами в `npm run build`.

## 3. Макети поза репозиторієм

**Дата:** 16.09.2026 · **Фаза:** 0

`design-source/` — 21 артборд, preview-сторінки й генератор на Node,
разом ~6 МБ. Це джерело дизайну, а не частина теми.

**Рішення.** Лежить локально в `themes/brix/docs/design-source/`,
додано в `.gitignore`. Усе, що з макетів потрібне продакшену, переноситься
в код: токени — в `assets/scss/abstracts/_tokens.scss`, компоненти —
в `assets/scss/components/`. Карта макетів, щоб не відкривати їх щоразу, —
в `03-makety.md`, і вона в репозиторії.

**Наслідки.** Репо лишається легким, в архів теми не потрапляє зайве.
Мінус — макети не видно на GitHub; це закриється скріншотами в README
на фазі 8.

## 5. Шрифти локальні, підмножини лише cyrillic і latin

**Дата:** 16.09.2026 · **Фаза:** 0

У макетах три сімейства підключені з Google Fonts. На проді це третій
домен у критичному шляху й мінус до LCP.

**Рішення.** 16 файлів `woff2` лежать у `assets/fonts/`, `@font-face`
компілюється з `assets/scss/base/_fonts.scss`, маніфест — `fonts.json`.
Перегенерація: `npm run fonts` (`tools/fonts.mjs`).

Беремо лише ті накреслення, що реально вживаються в макетах: Unbounded
700 і 800 (заголовки й логотип), Onest 400/500/600/700, IBM Plex Mono
400/500. Підмножини дві — `cyrillic` і `latin`: сайт двомовний UA/EN,
грецька, в'єтнамська й `latin-ext` йому ні до чого. Разом 385 КБ,
з яких на сторінку через `unicode-range` тягнеться лише частина.

У `preload` йдуть дві кириличні підмножини — Unbounded 800 і Onest 400:
це логотип, перший заголовок і навігація, тобто все, що впирається в LCP.

**Наслідки.** Оновлення шрифту вимагає запуску `npm run fonts` і коміту
бінарників. Перевіряти оновлення варто перед релізом: Google змінює
хеші URL при зміні версії шрифту.

## 6. Критичний CSS збирається, але поки не інлайниться

**Дата:** 16.09.2026 · **Фаза:** 0

`npm run build` збирає і `main.css`, і `critical.css` (шрифти, скидання,
типографіка, шапка). Але в `<head>` поки інлайниться не критичний CSS —
тема просто підключає `main.css` звичайним `wp_enqueue_style`.

**Чому так.** Інлайн критичного CSS має сенс лише в парі з відкладеним
завантаженням основного. Робити це наосліп, до перших замірів, — додати
14 КБ у кожну сторінку й ризик FOUC, не знаючи, чи це взагалі виграш.
Збірка готова, вмикання — задача фази 7, коли буде що міряти.

**Наслідки.** До фази 7 `critical.css` збирається «в стіл». Це свідомо:
дешевше тримати пайплайн готовим, ніж потім вбудовувати його заднім числом.

## 7. Тема не падає без WooCommerce і без brix-core

**Дата:** 16.09.2026 · **Фаза:** 0

**Рішення.** `functions.php` підключає `inc/woocommerce.php` лише якщо
`class_exists( 'WooCommerce' )`. Шаблони перевіряють `brix_has_woocommerce()`
перед викликом функцій Woo. Плагін `brix-core` без WooCommerce не
запускає модулі, а показує повідомлення в адмінці.

**Чому.** Кейс відкриють і поставлять на чисту інсталяцію. Білий екран
замість сайту через відсутній плагін — найгірше перше враження, яке
може справити репозиторій у портфоліо.
