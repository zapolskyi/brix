## 1. Один репозиторій над `wp-content`, а не окремо тема й плагін

**Дата:** 16.09.2026 · **Фаза:** 0

ТЗ вимагає і власну тему `brix`, і окремий плагін `brix-core`. У попередніх
проєктах (TORQ, Площина) git лежав у корені теми, бо тема була всім проєктом.
Тут так не вийде: половина логіки за задумом живе в плагіні.

**Рішення.** Git-корінь — `app/public/wp-content/`. `.gitignore` спершу
ігнорує все (`/*`), потім точково повертає `themes/brix/` і `plugins/brix-core/`.
Ядро WordPress, WooCommerce, аплоади й кеш у репозиторій не потрапляють.

**Альтернативи.**
- *Два репозиторії.* Два посилання в портфоліо і ручна синхронізація версій
  теми й плагіна, які змінюються одним і тим самим комітом.
- *Код плагіна всередині теми.* Суперечить меті кейсу — показати саме
  розділення презентації та бізнес-логіки.

**Наслідки.** Один `git log` на весь проєкт. README лежить у корені репо,
а не в темі. Архів для хостингу збирається окремо для теми й для плагіна.

## 2. Збірка на `sass` CLI, а не Vite

**Дата:** 16.09.2026 · **Фаза:** 0

ТЗ називало Vite. На TORQ перевірено простішу схему і вона вижила
до продакшену.

**Рішення.** `npm run css` компілює `assets/scss/main.scss` →
`assets/css/main.css`. **Скомпільований CSS комітиться в репозиторій.**
JS — ванільні файли без бандлера, підключаються там, де потрібні.

**Чому.** Тема має працювати на хостингу без Node. Заливаєш архів — сайт
живий. З Vite будь-який деплой вимагає кроку збірки, а забутий
`npm run build` дає сайт без стилів.

**Альтернатива.** Vite з `dist/` у `.gitignore` і збіркою в GitHub Actions.
Це правильно для застосунку, але надлишково для теми з одним CSS-файлом
і кількома скриптами.

**Наслідки.** У дифах з'являється скомпільований CSS — його не рев'ювимо,
дивимось лише на `.scss`. Hot reload немає, є `npm run css:watch`.
Мінімізація й критичний CSS — окремими скриптами в `npm run build`.

## 5. Шрифти локальні, підмножини лише cyrillic і latin

**Дата:** 16.09.2026 · **Фаза:** 0

У макетах три сімейства підключені з Google Fonts. На проді це третій
домен у критичному шляху й мінус до LCP.

**Рішення.** 16 файлів `woff2` лежать у `assets/fonts/`, `@font-face`
компілюється з `assets/scss/base/_fonts.scss`, маніфест — `fonts.json`.
Перегенерація: `npm run fonts` (`tools/fonts.mjs`).

Беремо лише ті накреслення, що реально вживаються в макетах: Unbounded
700 і 800 (заголовки й логотип), Onest 400/500/600/700, IBM Plex Mono
400/500. Підмножини дві — `cyrillic` і `latin`: сайт двомовний UA/EN,
грецька, в'єтнамська й `latin-ext` йому ні до чого. Разом 385 КБ,
з яких на сторінку через `unicode-range` тягнеться лише частина.

У `preload` йдуть дві кириличні підмножини — Unbounded 800 і Onest 400:
це логотип, перший заголовок і навігація, тобто все, що впирається в LCP.

**Наслідки.** Оновлення шрифту вимагає запуску `npm run fonts` і коміту
бінарників. Перевіряти оновлення варто перед релізом: Google змінює
хеші URL при зміні версії шрифту.

## 6. Критичний CSS збирається, але поки не інлайниться

**Дата:** 16.09.2026 · **Фаза:** 0

`npm run build` збирає і `main.css`, і `critical.css` (шрифти, скидання,
типографіка, шапка). Але в `<head>` поки інлайниться не критичний CSS —
тема просто підключає `main.css` звичайним `wp_enqueue_style`.

**Чому так.** Інлайн критичного CSS має сенс лише в парі з відкладеним
завантаженням основного. Робити це наосліп, до перших замірів, — додати
14 КБ у кожну сторінку й ризик FOUC, не знаючи, чи це взагалі виграш.
Збірка готова, вмикання — задача фази 7, коли буде що міряти.

**Наслідки.** До фази 7 `critical.css` збирається «в стіл». Це свідомо:
дешевше тримати пайплайн готовим, ніж потім вбудовувати його заднім числом.

## 7. Тема не падає без WooCommerce і без brix-core

**Дата:** 16.09.2026 · **Фаза:** 0

**Рішення.** `functions.php` підключає `inc/woocommerce.php` лише якщо
`class_exists( 'WooCommerce' )`. Шаблони перевіряють `brix_has_woocommerce()`
перед викликом функцій Woo. Плагін `brix-core` без WooCommerce не
запускає модулі, а показує повідомлення в адмінці.

**Чому.** Кейс відкриють і поставлять на чисту інсталяцію. Білий екран
замість сайту через відсутній плагін — найгірше перше враження, яке
може справити репозиторій у портфоліо.

## 8. Значення шкал передаються кастомними властивостями

**Дата:** 16.09.2026 · **Фаза:** 1

Шкали смаку, шкала °Bx і індикатор свіжості показують числа з паспорта
лоту: 4/5 кислотності, 22.4 °Bx, пік смаку з 21.09 по 12.10.

**Рішення.** Розмітка тримає лише структуру, а числа приходять
кастомними властивостями в `style`: `--brix-value` для шкал смаку,
`--brix-left` і `--brix-width` для діапазонів, `--brix-now` для позначки
«сьогодні». Рахує їх PHP з мета-полів товару.

**Альтернативи.** Inline `width: 80%` — те саме, але без назви, тож у
розмітці не видно, що це за число. Класи `.is-4-of-5` — комбінаторний
вибух і неможливість показати 22.4.

**Наслідки.** Один CSS-компонент обслуговує будь-які значення, а
верстальник бачить у розмітці осмислені імена. Мінус — inline `style`
у шаблоні; для CSP це означає `style-src 'unsafe-inline'` або nonce,
що вирішуватиметься на фазі 7.

## 9. Стани, яких немає в макетах, добудовуються при верстці

**Дата:** 16.09.2026 · **Фаза:** 1

Артборди статичні: у них немає ні `:hover`, ні `:focus-visible`,
ні помилок валідації, ні порожніх станів, ні «розпродано».

**Рішення.** Ці стани добудовуються при верстці й вважаються частиною
дизайн-системи, а не відходом від макета. Там, де добудова суперечить
макету, перемагає доступність.

Перший такий випадок — фокус полів. У макеті це рамка й ореол 8%
чорного; ореолу самого по собі мало, бо WCAG 2.2 вимагає 3:1 для
індикатора фокуса, а там близько 1.1:1. Ореол лишили, обведення додали.

**Наслідки.** UI-кіт у темі багатший за макет — у ньому є те, чого
в артбордах не малювали. Звіряти їх треба з цією поправкою.

## 10. Кастомні поля — Secure Custom Fields, але дані належать плагіну

**Дата:** 16.09.2026 · **Фаза:** 2 (ухвалено наперед)

ТЗ допускало «власний метабокс або ACF». Паспорт лоту — це 12 полів
на товар, плюс дані ферми, плюс кроки гайда з повторюваними рядками.

**Рішення.** Поля показує **Secure Custom Fields** — форк ACF від
WordPress.org. Групи полів реєструються **кодом** через
`acf_add_local_field_group()` у `brix-core`, а не кліками в адмінці:
так вони версіонуються в git і їдуть на staging разом з релізом,
а не переносяться експортом бази.

SCF 6.9.5+ містить теку `pro/` з `repeater`, `gallery`,
`flexible-content` і `clone` — можливості платної ACF Pro доступні
безкоштовно. API той самий, тож код лишається сумісним з ACF.

**Межа відповідальності.** SCF — це шар редагування, не шар даних.
Шаблони теми **не викликають `get_field()` прямо**: читання йде через
API плагіна (`LotMeta::for_product()` і подібні), який типізує
значення, підставляє дефолти й рахує похідні — вікно свіжості,
позиції на шкалах. Тому заміна SCF на власний метабокс чи на ACF
не зачепить жодного шаблону.

**Альтернативи.**
- *Власний метабокс.* У портфоліо виглядав би сильніше як демонстрація
  навички, але це тиждень роботи на repeater'и й валідацію заради
  функціонала, який уже існує й перевірений. Інженерне рішення тут —
  узяти готове й правильно відмежувати.
- *ACF Pro.* Платна, а переваг над SCF для цієї задачі не дає.

**Наслідки.** З'являється залежність від плагіна: без SCF поля не
редагуються. Тому `brix-core` перевіряє його наявність так само, як
перевіряє WooCommerce, і показує зрозуміле повідомлення замість фаталу.

**Про сам плагін.** SCF — це не сторонній ACF Pro. 2024 року, після
історії з WP Engine, WordPress.org форкнув Advanced Custom Fields
у Secure Custom Fields і виклав безкоштовно те, що було платним:
Flexible Content, Options Pages, ACF Blocks. Для проєкту 2026 року
платити за ACF Pro сенсу немає.

## 11. Три шари контенту, три різні рішення

**Дата:** 16.09.2026 · **Фаза:** 2 (ухвалено наперед)

Спокуса будь-якого проєкту з ACF/SCF — покласти в поля весь контент,
включно із заголовками секцій. Тоді редактор править сайт через
портянку з тридцяти інпутів, а блоковий редактор стоїть без діла.

**Рішення.** Контент ділиться на три шари, і кожен живе своїм способом.

| Шар | Приклад | Рішення |
|---|---|---|
| **Структуровані дані сутностей** | паспорт лоту, картка ферми, кроки гайда | SCF: справжні типи — число, реляція, повторювач |
| **Секції, що тягнуть дані** | «Вісім лотів, усі з паспортом», врізки ферм і гайдів | власні динамічні блоки з `block.json` + PHP render |
| **Маркетинговий текст** | заголовки, абзаци, картинки в секціях | нативний Gutenberg, без полів узагалі |

**Чому не SCF на все.** Заголовок секції вже редагується блоковим
редактором з коробки. Будувати поверх нього Flexible Content — подвійна
робота без жодної додаткової цінності.

**Чому не SCF-поля для сітки лотів.** Поле зі списком назв редактор
заповнить руками, і за тиждень воно розійдеться з каталогом. Динамічний
блок робить запит при кожному рендері, тож протухнути не може.

**Чому нативні блоки, а не ACF Blocks.** ACF Blocks швидші в написанні,
але прив'язують фронтенд до плагіна: вимкнув SCF — сторінка порожня.
З `block.json` і PHP render фронтенд не залежить від SCF узагалі,
а в кейсі видно знання Block API, а не «поставив плагін».

**Наслідки.** Блоків треба написати п'ять, і це довше, ніж намалювати
поля. Натомість головна лишається сторінкою в блоковому редакторі,
яку можна перебрати без розробника.

## 12. Порядок нот зберігається окремо від таксономії

**Дата:** 16.09.2026 · **Фаза:** 2

Під назвою товару стоять ноти: «Черешня · бергамот · молочний шоколад».
Порядок тут не випадковий — перша нота найпомітніша в чашці. А
`get_the_terms()` віддає терміни за абеткою, і виходило «бергамот ·
молочний шоколад · черешня».

**Рішення.** Таксономія лишається джерелом істини для фільтрів, а
порядок тримає окреме поле `brix_lot_notes` — SCF-поле типу `taxonomy`
з `multi_select`, яке зберігає ID у порядку вибору. `Lot::notes()`
сортує терміни за ним, а без нього лишається абетка.

Важлива деталь: `load_terms` у полі **вимкнено**. Увімкнений, він
щоразу перечитував би терміни з таксономії за абеткою і затирав
порядок, заради якого поле й існує. `save_terms` лишається увімкненим,
тож таксономія оновлюється при збереженні.

**Альтернативи.** Плагін на кшталт Simple Custom Post Order — зайва
залежність заради одного поля. Текстове поле з готовим рядком нот —
тоді ноти не фільтруються.

**Наслідки.** Дані лежать у двох місцях, і теоретично можуть розійтись.
Практично ні: таксономія пишеться з того самого поля при збереженні,
а `Lot::notes()` бере назви з таксономії й лише впорядковує їх полем.
Зайвий термін у таксономії просто поїде в кінець списку.

## 13. Стиль пачки задається і обробкою, і лінійкою

**Дата:** 16.09.2026 · **Фаза:** 2

Спершу колір пачки брався тільки з таксономії «Обробка»: natural —
Cherry, washed — Green Bean, honey — Honey. На імпорті виявилось, що
Panama Geisha з лінійки Lab виходить вишневою, бо оброблена вона
natural. А в брендбуку Lab має темне пакування незалежно від обробки.

**Рішення.** `Lot::pack_style()` дивиться спершу на категорію товару,
потім на обробку. Мета-поле `brix_pack_style` є і в термінів обробки,
і в категорій; Lab, Core і Drip & Try мають власні стилі, Origin
свого не має — там колір бере обробка.

**Наслідки.** Обидві таксономії редагуються з адмінки, тож нову лінійку
чи обробку можна додати без правок CSS. Мінус — стиль тепер шукається
у двох місцях, і за пріоритетом треба йти в код.

## 14. Кошик і checkout — класичні шаблони, не блокові

**Дата:** 17.09.2026 · **Фаза:** 3А

WooCommerce 11 створює сторінки кошика й checkout блоками. Блоковий
checkout малюється скриптом: у HTML лежить порожній контейнер, вміст
приходить через Store API. Це напряму суперечило критерію фази 3 —
сайт має працювати з вимкненим JavaScript.

**Рішення.** Сторінки переведені на шорткоди `[woocommerce_cart]`
і `[woocommerce_checkout]`, шаблони перевизначені в темі.

**Чому.** Три причини, у порядку ваги:

1. **Без JS блоковий checkout — порожня сторінка.** Не «гірше
   виглядає», а купити неможливо.
2. **Артборди.** Кошик у макеті — це рядок із пачкою, назвою й помелом,
   прогрес до безкоштовної доставки, upsell. У блоковому checkout така
   розкладка вимагає писати розширення на React; у класичному це
   override шаблону.
3. **Нова Пошта у фазі 5.** У класичному checkout вибір відділення —
   це `woocommerce_form_field()` і трохи JS. У блоковому — окремий
   плагін-розширення з реєстрацією полів у Store API.

**Альтернативи.**
- *Блокові, як у ТЗ.* Сучасніший шлях WooCommerce, Apple Pay і Google
  Pay з коробки. Але критерій фази довелося б переписати, а екрани
  вийшли б не за макетом.
- *Класичні зараз, блокові потім другим шляхом.* Обидва в кейсі, але
  подвійна робота на checkout і подвійна інтеграція Нової Пошти.

**Наслідки.** Це відхід від букви ТЗ, позначений 📌 у
`02-tehnichne-zavdannya.md`. WooCommerce називає класичний checkout
legacy, тож у README кейсу це варто пояснити одним абзацом — інакше
виглядатиме як незнання сучасного стеку, а не як зважений вибір.

Apple Pay і Google Pay доведеться підключати через Stripe окремо,
а не отримати даром разом з express-payment блоком.

## 15. Селектор варіацій рахує сервер, а не скрипт

**Дата:** 17.09.2026 · **Фаза:** 3А

Стандартна форма варіативного товару WooCommerce без JavaScript не
працює взагалі: вагу й помел обирає скрипт, він же підставляє
`variation_id` у прихованому полі.

**Рішення.** Вибір їде в адресному рядку
(`?attribute_pa_weight=250-h&attribute_pa_grind=espreso`), сервер
знаходить варіацію через `find_matching_product_variation()` і малює
ціну, наявність та кнопку саме для неї. Кожен варіант ваги — звичайне
посилання на той самий товар з іншим набором параметрів.

**Наслідки.** Зміна ваги коштує перезавантаження сторінки — на фазі 4
AJAX його прибере, але логіка підбору лишиться серверною, бо посилання
на конкретну комбінацію має лишатись робочим.

Заразом з'явився побічний виграш: посиланням «Ethiopia Guji, 250 г,
еспресо» можна поділитись, і воно відкриється саме таким.

Атрибути довелося перевести з локальних на глобальні: локальні
зберігають кириличну назву, і в адресі виходило
`attribute_%d0%b2%d0%b0%d0%b3%d0%b0`.

## 16. Секції головної — власні динамічні блоки, а не поля

**Дата:** 17.09.2026 · **Фаза:** 3В

Рішення 11 поділило контент на три шари, але залишило відкритим, чим
саме робити третій — секції, які самі ходять у базу за товарами.

**Рішення.** Власні динамічні блоки на рідному Block API: `block.json`
з атрибутами плюс `render.php`, який малює розмітку на сервері при
кожному запиті. Шість блоків: `hero`, `marquee`, `lot-grid`, `feature`,
`farm-teaser`, `brew-guide`. У базі лишається лише рядок налаштувань:
`<!-- wp:brix/lot-grid {"limit":4,"category":"origin"} /-->`.

**Альтернативи.**
- *ACF/SCF Blocks.* Швидше писати, менше коду. Але фронтенд стає
  залежним від плагіна: вимкнув SCF — головна порожня.
- *Поля SCF на сторінці головної.* Фіксований набір секцій у
  фіксованому порядку. Додати другу сітку лотів неможливо без коду.
- *Хардкод у `front-page.php`.* Найшвидше, але тоді редактор нічого
  не змінює, а в кейсі це головна претензія до саморобних тем.

**Наслідки.** Розмітка існує рівно в одному місці — у PHP, і перегляд
у редакторі малює `ServerSideRender` тим самим кодом. Редактор фізично
не може розійтися з фронтендом, на відміну від звичайної схеми, де
`edit` на React і `save` на PHP — це дві реалізації, що повільно
розходяться.

Ціна — 560 рядків на шість блоків: 24–56 рядків `block.json` і 70–85
рядків `render.php` на кожен, плюс 309 рядків спільного каркаса,
написаних один раз.

Перегляд у редакторі ходить на сервер за кожної зміни атрибута. Для
шести секцій головної це непомітно; якби блоки ставили в цикл по
сотні на сторінку, довелося б писати `edit` окремо на JS.

## 17. Редакторський скрипт без збірки — `createElement` замість JSX

**Дата:** 17.09.2026 · **Фаза:** 3В

`"editorScript": "file:./editor.js"` у `block.json` очікує поряд
`editor.asset.php` зі списком залежностей — його генерує
`@wordpress/scripts`, тобто webpack.

**Рішення.** Скрипт реєструється вручну в `inc/blocks.php` з явним
переліком залежностей (`wp-blocks`, `wp-element`, `wp-block-editor`,
`wp-components`, `wp-server-side-render`, `wp-i18n`), а сам файл
написаний на `wp.element.createElement` без JSX — один спільний
модуль на всі шість блоків.

**Альтернативи.** Поставити `@wordpress/scripts` — це node_modules на
~200 МБ і другий інструмент збірки поряд з `sass` CLI заради 196 рядків
коду. Проєкт свідомо тримається на одному `sass` (рішення 3).

**Наслідки.** Файл читається як є, без кроку компіляції — узгоджено
з тим, що скомпільований CSS теж комітиться. Мінус: `createElement`
з вкладеністю читається гірше за JSX, тож на більшому обсязі блоків
рішення довелося б переглянути.

Три вади, які знайшлись лише при відкритті редактора людиною:

- **`add_theme_support('editor-styles')` не було** — редактор не бачив
  CSS теми й показував блоки голим serif-текстом.
- **BOM на початку `main.css`.** `sass` дописував `EF BB BF`; у
  зовнішньому файлі браузер його знімає, але редактор вставляє стилі
  інлайном, і BOM ламав найперше правило `:root` — а це всі токени.
  Лікується прапорцем `--no-charset`.
- **`useBlockProps()` у `edit` був обов'язковим.** Без нього блок
  рендериться, але не виділяється: клік потрапляє в текст, панель
  справа лишається порожня. Помилки в консолі немає.

## 18. Оплата й доставка: monobank, Нова Пошта, накладний платіж

**Дата:** 17.09.2026 · **Фаза:** 5 (ухвалено заздалегідь)

ТЗ у розділі E давало вибір «LiqPay або monobank», у розділі F вимагало
власну інтеграцію з Новою Поштою. Оплату при отриманні ТЗ не згадувало
взагалі — вона додалась як побажання після перегляду верстки.

**Рішення.**

*Онлайн-оплата — monobank Acquiring.* Створюємо інвойс запитом до API,
покупця відправляємо на платіжну сторінку monobank, підтвердження
приймаємо вебхуком. Stripe лишається для зони ЄС, як у ТЗ.

*Нова Пошта — власна інтеграція під справжній API,* але з довідником
міст і відділень у базі. Ключ підставляється константою; поки його
немає, автокомпліт працює з локального довідника, а не з заглушки.

*Оплата при отриманні — до певної суми.* Дрібне замовлення можна взяти
накладним платежем, велике йде передоплатою. B2B, як і в ТЗ, — за
рахунком.

*Комісію за накладний платіж платить магазин.* У підсумках кошика
її немає, ціна не залежить від способу оплати.

**Альтернативи.**
- *LiqPay.* Ширше покриття серед покупців, але підпис формується
  вручну з base64 і SHA-1, і тестовий режим менш зручний. Для
  портфоліо-проєкту це зайва морока без виграшу в кейсі.
- *Обидві платіжки на вибір.* Виглядало б солідніше, але це подвійна
  інтеграція й два тестові акаунти заради однієї галочки.
- *Накладний платіж без обмеження суми.* Найпростіше правило, але
  неотримана посилка зі змеленою під V60 кавою — це прямий збиток:
  такий лот не перепродаси.
- *Комісія на покупця.* Чесніше, але додає рядок у підсумки й
  прив'язує суму до способу оплати — у кошику це видно й дратує.

**Наслідки.**

Платіжних даних на нашому сервері не буде взагалі: картку покупець
вводить на сторінці monobank. Це знімає і питання PCI, і половину
роботи — але вимагає коректно обробити повернення з платіжної
сторінки й вебхук, включно з випадком, коли покупець закрив вкладку.

Обмеження суми для накладного платежу — це бізнес-правило в коді,
тож поріг має жити в налаштуваннях, а не в константі: інакше його
не змінити без деплою.

Оплата при отриманні — відхід від ТЗ, позначений 📌 у
`02-tehnichne-zavdannya.md`, як і класичний checkout.

## 19. REST-ендпоінти каталогу й картки живуть у темі, а не в плагіні

**Дата:** 21.09.2026 · **Фаза:** 4

План називав модуль `Catalog/FilterController` у плагіні `brix-core`.
Але ендпоінт фільтрації віддає не дані, а **розмітку**: сітку карток,
чипи активних фільтрів, сайдбар. Те саме з ендпоінтом картки товару —
він віддає блок покупки.

**Рішення.** Обидва ендпоінти в темі: `inc/catalog-rest.php` і
`inc/product-rest.php`. Плагін лишається шаром даних, тема — шаром
представлення.

**Альтернативи.**
- *Контролер у плагіні, як у плані.* Тоді плагін викликав би шаблонні
  частини теми — залежність задом наперед: плагін мусив би знати імена
  файлів теми й ламався б від їх перейменування.
- *Ендпоінт віддає JSON, розмітку збирає JavaScript.* Канонічний
  поділ, але тоді розмітка існує двічі: у PHP для сторінки й у JS для
  оновлення. Дві копії розходяться — це та сама причина, з якої
  блоки у фазі 3 зроблені динамічними (рішення 16).

**Наслідки.** Відповідь важча за JSON: замість списку ідентифікаторів
летить готовий HTML. Для каталогу на 14 лотів це несуттєво, але якби
сторінка віддавала сотні карток, довелось би віддавати тільки сітку,
а не всі чотири шматки одразу.

Натомість перевірка стала простою й сильною: кожен шматок відповіді
має дослівно збігатися з тим, що є на сторінці. Саме так і перевірено —
12 сценаріїв, нуль розбіжностей.

Щоб це працювало, довелось прибрати читання `$_GET` із фільтрів і
з підбору варіації: стан приходить через `brix_catalog_request()` і
`brix_variation_request()`, а джерело підмінне. Інакше логіка
роздвоїлася б на «для сторінки» і «для REST».

## 20. Довідник Нової Пошти живе в нашій базі, а ключ не їде на сервер

**Дата:** 22.09.2026 · **Фаза:** 5

Нова Пошта видає **один** ключ на бізнес-кабінет — створити другий під
демо-стенд неможливо. Той самий ключ уже працює в іншому проєкті, і
квота в них спільна.

А маршрут підказок у нас відкритий: інакше гість не заповнив би
checkout. Тобто будь-хто міг слати унікальні запити, проходити повз
кеш і витрачати квоту чужого робочого проєкту.

**Рішення.** Довідник вивантажується командою `wp brix np-sync` у власну
таблицю. Автокомпліт читає її, а не API. Ключ потрібен лише на машині,
де запускають синхронізацію, і читається з константи
`BRIX_NOVA_POSHTA_KEY` у `wp-config.php` — не з бази.

**Альтернативи.**
- *Лишити живий API з кешем.* Кеш рятує від повторів, а не від
  перебору. І ключ довелося б везти на публічний сервер, де його видно
  з адмінки й у кожному бекапі.
- *Створити окремий ключ під демо.* Неможливо: кабінет дозволяє по
  одному ключу на сервіс.
- *Синхронізувати тільки великі міста.* Менше даних, але покупець із
  невеликого міста не знайшов би свого відділення — і це було б видно
  в демонстрації.

**Наслідки.** Довідник застигає на даті синхронізації: нові відділення
не зʼявляться, поки не запустити команду знову. Для демо-стенду це не
проблема, для справжнього магазину — щотижневий cron.

Ключ Нової Пошти дає право створювати накладні, а не лише читати
довідник. Саме тому його місце в конфігу, а не в `wp_options`: базу
видно всім, хто має доступ до адмінки.

Заразом на маршрут додано обмеження частоти — двадцять запитів на
хвилину з адреси. Живому покупцю цього вистачає з запасом, перебору — ні.

## 21. LiqPay замість Stripe, і обидві платіжки свої

**Дата:** 22.09.2026 · **Фаза:** 5

ТЗ відводило Stripe зону ЄС, а monobank — Україну. Stripe так і не був
написаний: жодного рядка коду, тільки згадки в документації.

**Рішення.** Stripe виходить, LiqPay заходить. Обидві платіжки — власні
інтеграції: monobank для України, LiqPay як другий спосіб і для
міжнародних карток.

**Чому не готові плагіни.** На стенді вже стояли `mrkv-liqpay-extended`
і `wc-ukr-shipping` — робочі плагіни, які закрили б обидві задачі
встановленням. Відмовились із трьох причин:

- Наш checkout перероблений: прибрані компанія, друга адреса й
  область, «Адреса» перейменована під відділення. Плагін додав би свої
  поля міста й відділення — рівно та помилка, яку я вже зробив і
  відкотив, побачивши дубль на знімку.
- Сайт працює без JavaScript, і це головне обмеження проєкту.
  Перевірити на цю вимогу чужий код довше, ніж написати свій.
- Це портфоліо. У 250 рядках інтеграції видно роботу з вебхуками й
  перевірку підробленого статусу; у рядку «встановив плагін» не видно
  нічого.

**Наслідки.** Два способи оплати замість одного — більше коду, але й
запасний варіант, якщо один провайдер недоступний.

Механіка в них різна, і це видно в коді. monobank створює інвойс
запитом і віддає адресу сторінки оплати; статус ми не приймаємо з
вебхука, а перепитуємо в API. LiqPay інвойсів не має — форма з полів
`data` і `signature`, а callback підписаний нашим приватним ключем,
тож підпис перевіряється локально, без звернення назовні.

В обох випадках картка вводиться на боці платіжної системи, і
платіжних даних на нашому сервері не буває.

## 22. Спосіб отримання вирішує, які поля показувати

**Дата:** 23 вересня 2026
**Статус:** ухвалено

**Проблема.** Checkout питав адресу й відділення незалежно від того,
що обрав покупець. На самовивозі «Адреса або відділення» лишалось
обов'язковим, помічене червоним, — людина, яка збирається зайти на
Кирилівську сама, мусила вигадати туди відділення Нової Пошти. Сам
вибір способу стояв у правій колонці, в підсумку замовлення: рішення
внизу праворуч, наслідок — угорі ліворуч.

У кошику до двох способів додавався третій рядок, «Безкоштовна
доставка». Це не третій спосіб, а та сама Нова Пошта без оплати, але
з назв це не читалось, і поруч стояли «Нова Пошта — 80 ₴» і
«Безкоштовна доставка» з однаковою вагою.

**Рішення.** Спосіб отримання — перший блок лівої колонки, дві
картки. Далі «Отримувач» (ім'я, телефон, пошта) і «Куди доставити»
(країна, місто, відділення). Останній блок зникає на самовивозі, а
замість нього під картками розкривається плашка: адреса, години,
строк готовності.

Безкоштовна ставка не додається до платної, а **займає її місце** й
бере її назву. Способів завжди рівно два.

**Чому поля ховаються, а не видаляються.** Видалені довелось би
відтворювати з нуля разом із набраним текстом, коли покупець передумає.
Тож розмітка завжди повна, а стан задає сервер: на самовивозі поля
необов'язкові й приховані, а те, що в них лишилось, стирається у
`woocommerce_checkout_posted_data` — інакше стара адреса поїхала б у
замовлення, якого ніхто не замовляв.

**Без JavaScript** спосіб перемикає кнопка «Оновити» —
`woocommerce_checkout_update_totals`, власний механізм WooCommerce.
Він проходить повну перевірку форми, тож зауваження на цьому кроці
глушаться: людина натиснула «Оновити», а не «Підтвердити замовлення».

**Наслідок, якого не було видно.** У класичному checkout WooCommerce
підставляє **першу ставку пакунка** як обрану за замовчуванням. Доки
безкоштовна доставка просто витісняла платну в кінець списку, першим
лишався самовивіз — і покупець зі Львова, не придивившись, замовив би
забрати каву в Києві. Тому підстановка зберігає позицію.

## 23. Двомовність без другого дерева записів

**Дата:** 23 вересня 2026
**Статус:** ухвалено

**Проблема.** У шапці з першого дня стояло «UA / EN», але це був
просто текст. Треба було зробити другу мову справжньою — інтерфейс,
контент, адреси, листи.

**Чому не Polylang і не WPML.** Безкоштовний Polylang не перекладає
товари WooCommerce — для цього потрібне платне доповнення. Але річ
навіть не в грошах: обидва плагіни тримають переклад **окремим
записом**. Для магазину це означає другий товар з власним
ідентифікатором, власними залишками й власним кошиком — і постійну
роботу з тримання їх синхронними. Наші власні REST-ендпоінти, квіз і
фільтри каталогу довелося б навчати мові однаково в будь-якому разі.

**Рішення.** Переклад лежить у мета-полі поруч з оригіналом і
підставляється на читанні. Товар один, залишок один, кошик один, а
`/shop/lot` і `/en/shop/lot` — це той самий запис.

**Ціна рішення.** Переклад не має власного статусу публікації: його
не можна тримати в чернетці, поки оригінал живий. Для двох мов і
двох десятків сторінок це дешевше, ніж дзеркальне дерево записів.

**Адреси.** Уся маршрутизація тримається на одному фільтрі —
`home_url`. WordPress будує з нього майже кожну адресу на сайті, тож
префікс `/en` з'являється всюди сам: у посиланнях на товари, у
пагінації, у діях форм, у маршрутах REST. Розбір запиту працює звідти
ж: `WP::parse_request()` відрізає шлях `home_url()` перед пошуком
правила перезапису, тому `/en/shop/` перетворюється на `shop/` і
маршрутизується як завжди. Власних правил перезапису — жодного.

**Три шари тексту.** Інтерфейс — у `.po`, де msgid український, бо
оригінал тут українською. Контент — у мета-полях записів і термінів.
Те, що лежить у налаштуваннях і чого `.po` не бачить (назви способів
доставки, підписи платіжок, значення за замовчуванням в атрибутах
блоків) — у таблиці рядків, ключ якої і є український оригінал.

**Листи.** Мова запиту тут не підходить: лист про зміну статусу
надсилає крон. Тому мова записується в замовлення при оформленні.
Покупець отримує лист своєю мовою, власник магазину — завжди
українською: `woocommerce_allow_switching_email_locale` спрацьовує на
кожен лист окремо й знає, кому він адресований.

**Валюта.** Друга половина пункту 7.5 — у [рішенні 24](#24-євро-як-друга-валюта-без-другої-ціни).

## 24. Євро як друга валюта — без другої ціни

**Дата:** 23 вересня 2026
**Статус:** ухвалено

**Проблема.** Англійська версія показувала гривні. Для магазину, який
возить каву в ЄС, це та сама половинчастість, що й «UA / EN» звичайним
текстом у шапці.

**Рішення.** Ціна в базі одна — гривнева. Євро рахується на читанні за
курсом з налаштувань. Зміна курсу не вимагає переписувати чотирнадцять
товарів і дев'яносто варіацій, а поле ціни лишається одне.

Плата — копійки після ділення: 620 ₴ за курсом 48 дають 12,92 €, і
сума трьох таких пачок на цент розходиться з ціною, перерахованою від
1 860 ₴. Для другої валюти це дешевше за окреме поле ціни в кожній
варіації, яке хтось муситиме тримати актуальним.

**Валюта прив'язана до мови,** а не до країни. Визначати країну за IP
означає помилятися на кожному VPN, а другий перемикач поруч із мовним —
два питання там, де покупець прийшов по каву.

**Замовлення зберігає свою валюту.** У полі замовлення лежить EUR, і
лист, адмінка та повернення показують євро навіть тоді, коли решта
сайту рахує в гривні.

**Точність переїхала з бази на показ.** У магазину стояло нуль знаків
після коми — гривневі ціни цілі. Але WooCommerce округлює до цієї
точності **самі суми**, не тільки їх вигляд: замовлення на 14,17 €
зберігалось як 14 €. Тепер у налаштуваннях дві цифри, а гривню без
копійок малює `wc_price_args` — фільтр, який дивиться на валюту самої
суми, а не на мову сторінки. Тому євро в українському списку замовлень
теж лишається з центами.

**Що виявилось по дорозі.** Дві речі мовчки ламались від переведення,
і обидві — про те, що число з бази й число на екрані більше не одне й
те саме:

- Фільтр ціни в каталозі порівнював введені євро з гривневим `_price`.
  «До 15» відсікало все, що дорожче за 15 гривень.
- Бюджет у квізі порівнював гривневу стелю з євровою ціною лоту, тож
  відповідь про бюджет переставала впливати на порядок узагалі.

А ще розбір ваги варіації шукав у назві терміна «кг» і «г». Під /en/
назва приходить перекладеною — «250 g», — і вага ставала нулем. Разом
з нею зникали ціна за кілограм на сторінці прозорості й мінімум 5 кг
для оптовиків.

**Чого свідомо немає.** Поновлення підписки створює замовлення з
крона, де мови запиту немає, — воно виходить гривневим навіть для
підписки, оформленої англійською. Для демо це прийнятно; для бойового
магазину мову підписки довелося б запам'ятовувати так само, як мову
замовлення.

## 25. Два способи оплати, і жодного переказу

**Дата:** 23.09.2026 · **Фаза:** 7

Рішення 21 залишило магазин із карткою й накладним платежем. Коли
з'явилась доставка за кордон, виявилось, що для покупця з ЄС не
працює жоден із них: накладний платіж — послуга Нової Пошти, а
картка тоді ще чекала на ключі. Тимчасовою латкою став банківський
переказ, увімкнений тільки для закордонних адрес.

**Рішення.** Ключі LiqPay отримано, тож латку знято. Лишаються два
способи: **картка онлайн — скрізь**, **оплата при отриманні — лише
по Україні**. Модуль `Payments\BankTransfer` видалено, сам переказ у
WooCommerce вимкнено.

**Чому не лишити переказ як третій варіант.** Він виглядає як спосіб
оплати, але ним не є: ніщо в сайті не знає, чи гроші прийшли. Власник
мусить щодня звіряти виписку й руками міняти статус. Для магазину на
двох людей це не процес, а обіцянка, яку ніхто не виконуватиме. Один
неоплачений переказ коштує дорожче, ніж уся економія на комісії.

**Що це полагодило дорогою.** Поріг накладного платежу (рішення 18)
досі не працював. Він знімає накладний платіж із дорогих замовлень,
але лише якщо покупцю лишається чим платити, — а поки картки не було,
лишатись не було чому, і поріг мовчки не спрацьовував жодного разу.
Тепер замовлення на 7 400 ₴ справді пропонує тільки картку.

**Наслідки.**

- Без ключів LiqPay закордонне замовлення знову лишається без оплати.
  Це видно покупцю: `CashOnDelivery` показує пояснення, а не порожнечу.
- Сторінка оплати LiqPay тепер відкривається мовою замовлення, а не
  завжди українською. Мова береться з мети `_brix_lang` самого
  замовлення, а не з поточного запиту: покупець може повернутись до
  оплати з листа через день.
- Адреса, на яку LiqPay стукає з відповіддю, більше не має префікса
  `/en/`. Її читає чужий сервер і зберігає в себе надовго —
  прив'язувати її до нашого способу робити двомовність не варто.

## 26. Валюта окремо від мови

**Дата:** 23.09.2026 · **Фаза:** 7 · **Уточнює:** рішення 24

Рішення 24 прив'язало євро до англійської версії: другий перемикач
поруч із мовним здавався зайвим питанням. На живих сценаріях це
ламалось:

- англомовний покупець у Києві отримував ціни в євро для посилки
  Новою Поштою — і накладний платіж у євро, якого Нова Пошта не
  приймає;
- українка у Варшаві читала сайт українською й не могла побачити
  ціну у валюті, якою платить.

**Рішення.** Мова — про те, як людина читає; валюта — про те, чим
вона платить. Перемикач «₴ / €» стоїть поруч із «UA / EN». Без вибору
валюта, як і раніше, випливає з мови, тож для того, хто перемикачем
не користується, нічого не змінилось.

**Як влаштовано.** Вибір живе в куці `brix_currency`. Перемикач —
звичайне посилання `?currency=eur`: сервер записує куку й одразу
перенаправляє на ту саму адресу без параметра, тож працює без
JavaScript і не плодить адрес у закладках. Адмінка, крон і WP-CLI
завжди в гривні.

**Альтернативи.** Валюта за країною доставки — міняла б усі ціни
посеред оформлення, щойно покупець обрав країну. Визначення країни за
IP — помиляється на кожному VPN.

**Наслідки.**

- Мова в адресі, валюта в куці — сторінковий кеш має розрізняти
  куку. Для LiteSpeed Cache це робить фільтр `litespeed_vary_cookies`.
- Накладний платіж у євро прибирається з поясненням, як його
  повернути.

## 27. Оплату підтверджує той, хто першим дізнається

**Дата:** 23.09.2026 · **Фаза:** 7

LiqPay повідомляє про оплату callback-ом на сайт. Але callback
приходить лише на адресу, видиму з інтернету, і часто пізніше, ніж
покупець повертається на сайт. А повертається він не сам: LiqPay після
оплати лишається на власній сторінці «Дякуємо!» і веде назад тільки
кнопкою.

**Рішення.** Сторінка подяки, відкриваючись, сама питає LiqPay про
статус платежу (`action: status`) і застосовує його через ту саму
функцію, що й callback. Хто б не дізнався першим — оплата
зараховується один раз: `payment_complete` для вже оплаченого
замовлення нічого не робить.

**Тонкість.** Для замовлення, яке ще не оплачували, LiqPay відповідає
статусом `error` з кодом `payment_not_found`. Перепитування його
ігнорує: позначити таке замовлення невдалим означало б відібрати в
покупця можливість оплатити пізніше.

**Наслідки.** Повний цикл оплати працює й на локальному сайті, без
публічної адреси. Подяка має третій стан — «Оплата ще не
підтверджена», — замість того щоб обіцяти «Смажимо й відправляємо»
за неоплачене замовлення.

## 28. Розсилка: подвійне підтвердження, список — у сайті, листи — ні

**Дата:** 23.09.2026 · **Фаза:** 7

Форма «Лист у понеділок» у підвалі від фази 3 відправлялась на «#»:
адреса зникала, людина не бачила жодного відгуку.

**Рішення.** Адреса → лист «Підтвердіть підписку» → клік → підписку
підтверджено. Кожен крок закінчується повідомленням на місці форми
(якір `#brix-newsletter`). Відписка — посиланням з будь-якого листа,
запис видаляється зовсім. Підписники — приватний тип записів
`brix_subscriber`, як і заявки B2B: список в адмінці «Розсилка»,
вивантаження підтверджених у CSV.

**Чому подвійне підтвердження.** Без нього будь-хто підписав би чужу
адресу, а політика конфіденційності обіцяє лист лише тим, хто на
нього підписався.

**Чому без nonce.** Підвал стоїть на кожній сторінці, сторінки
кешуються, і nonce у кеші протухав би за добу — форма ламалась би
саме на тих сторінках, що відвідують найчастіше. Від ботів захищають
приманка й ліміт 5 спроб на годину з IP, від чужих адрес —
підтвердження.

**Чого свідомо немає.** Самі понеділкові листи сайт не розсилає: це
робота сервісу розсилок з його доставлюваністю й статистикою.
Власник вивантажує CSV і завантажує туди.

## 29. Кабінет: гостем можна, з підпискою — ні

**Дата:** 23.09.2026 · **Фаза:** 7

Реєстрацію було вимкнено скрізь — і на сторінці кабінету, і на
checkout. Кабінет бачили лише демо-акаунти. Гірше: гість міг
оформити підписку BRIX Club зі знижкою −10%, а підписка створюється
лише для замовлення з покупцем. Покупець вважав себе підписаним, сайт
про підписку не знав.

**Рішення.**

- Купувати гостем — можна. Змушувати реєструватись заради пачки
  кави — зайвий бар'єр.
- Кабінет — за бажанням: на сторінці входу й галочкою на checkout.
  Реєстрація просить лише пошту; пароль покупець задає за посиланням
  із листа, логін WooCommerce складає сам, а входити можна поштою.
- З підпискою BRIX Club у кошику кабінет обов'язковий, і checkout
  каже чому. Робить це модуль `Club\Plan`, а не налаштування: правило
  стосується лише кошика з підпискою.
- Гостьові замовлення на ту саму пошту прив'язує WooCommerce 11, щойно
  пошту підтверджено, а підтвердженням є пароль, заданий за посиланням.

**Наслідки.** Вагу чи помел, на які оформлено підписку, власник може
зняти з продажу. Раніше підписка тоді показувала «Лот недоступний», а
поновлення мовчки нічого не робило й не переносило дату — підписка
тихо вмирала. Тепер кабінет називає лот і просить обрати заново, а
поновлення відкладається на цикл.

## 30. Пошта через API Brevo, без SMTP-плагіна

**Дата:** 23.09.2026 · **Фаза:** 7

PHP-пошта шаред-хостингу — найкоротший шлях у спам, а лист «задайте
пароль» чи «замовлення прийнято», що не дійшов, ламає покупку.

**Рішення.** Модуль `Mail\Brevo` перехоплює `wp_mail()` фільтром
`pre_wp_mail` і відправляє через транзакційний API Brevo. Одна точка
покриває листи WooCommerce, WordPress і власні — розсилку, Club,
нагадування.

**Чому не SMTP-плагін.** Ще один плагін із власною адмінкою, де ключ
лежить у базі — а отже й у кожному бекапі. Тут ключ — константа у
`wp-config.php`, як і ключ Нової Пошти, і на сервер його кладуть
руками.

**Деталі.**

- Відправник завжди підтверджена адреса (`BRIX_BREVO_SENDER`), ім'я —
  те, яким лист підписав WooCommerce. Вигадана `hello@brix22.coffee`
  з налаштувань Brevo відхилив би.
- Листи на домени, що пошти не приймають (`example.com`, `.local`,
  `.test`), ідуть повз Brevo: інакше кожен лист демо-акаунтам — це
  відмова в репутацію відправника.
- Brevo не відповів — лист іде поштою хостингу, а збій пишеться в
  журнал WooCommerce. Краще лист зі спаму, ніж жодного.
